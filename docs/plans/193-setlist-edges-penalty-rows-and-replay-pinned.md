### What is wrong

- `setlistfm.ts`'s request carries `signal: AbortSignal.timeout(REQUEST_TIMEOUT_MS)` (`:440`); delete it, or change the constant, and no test fails, so the ten-second bound the release notes state is unguarded. `retryDelay` gives up when `retryAfterMs > MAX_BACKOFF_MS` (`:408`): a `Retry-After` of exactly 5 s is retried today and would be refused under `>=`, and no test uses 5 (they use 2, 3, 60, 120). `parseRetryAfter(..., Date.now())` (`:461`): replace `Date.now()` with `0` and the HTTP-date path through the client is untested.
- `VARIANT_PENALTIES` (`matching.ts:76-85`): delete the commentary, instrumental, remix, demo, sped-up, made-popular-by or tribute row and no test fails (the existing penalty tests cover karaoke, in-the-style-of, originally-by and live). Drop the `suite` argument from the sibling `titleScore` call (`:304`) and no test fails. Drop `MAX_DESCRIPTION_LENGTH` clipping in `playlistDescription` (`build.ts:143-149`) and no test fails (only the name clip is tested).
- `replay.test.ts` pins each song's pick but only prints `unserved` (`:34-35`, `:56`, `:121-122`): a changed query string makes every page unserved and every `missing` entry still passes. The tally assertion lives in `afterAll` (`:119-134`); that its failure fails the run is inferred, not verified. `findSong` is called without `artists` (`:94-98`), so the fallback-name chain is invisible to the replay.

### Decisions

- **Constants are exported and pinned where waiting would be the only alternative.** `export const REQUEST_TIMEOUT_MS` in `setlistfm.ts` and `export const MAX_DESCRIPTION_LENGTH` in `build.ts` (read-only exports, no logic change); the timeout test asserts the request's `init.signal` is an `AbortSignal` that is not yet aborted, and that the constant is `10_000`. A real ten-second wait is not a test.
- **The boundary and the date path go through the real client,** with the `scripted` harness at `setlistfm.test.ts:498-515`: `Retry-After: 5` is slept for `5000`, `Retry-After: 6` gives up at once; an HTTP-date two seconds ahead of now sleeps between 1000 and 2000 ms.
- **The penalty rows are pinned as a table on `explainCandidate(...).penalty`,** one case per row and one for the exemption (a marker that is in the song's own title costs nothing), so #191's change to how `pickBestTrack` treats a 100-point penalty does not affect them.
- **The replay asserts what it served.** Each song's test records `unserved.length` before `findSong` and asserts it unchanged afterwards, for every entry; if a `missing` entry's logged pages genuinely stop short of a query `findSong` issues, restrict that one entry with a comment naming it, and say so in the PR. The tally moves from `afterAll` into a final `test("the tally is what the baselines say")` (the `afterAll` keeps its `console.log` lines). **The fallback-chain replay is declined:** the corpus holds no performer names (its shape test at `:77-82` forbids extra keys) and the 2026-09-25 logs hold no fallback-query pages, so a second replay would need a new corpus; that is its own child if ever wanted, and the PR says so.

## Deviations as implemented

- **The HTTP-date test pins the clock.** It spies on `Date.now` and expects the sleep to be exactly `[2000]`, not "between 1000 and 2000": `toUTCString()` truncates to the second, so a live-clock header can fall a few milliseconds short of the plan's lower bound. Same method as the Spotify client's date test (#192).
- **The timeout test also spies on `AbortSignal.timeout`.** Besides the plan's checks (`init.signal` is a live `AbortSignal`, `REQUEST_TIMEOUT_MS` is `10_000`) it asserts the spy saw `[[10_000], [10_000]]` over two calls, so the signal is built from the ten-second bound on every request and not merely present.
- **One extra penalty row.** The table also covers `originally by`, the second spelling of `originally (performed )?by`; the plan listed only `originally performed by`.
- **The suite tie-break test also asserts the whole-suite candidate's own title is 60,** so the case cannot pass by some other route than the suite rule.
- **The description clip has a boundary test the plan did not list:** a description of exactly 300 characters is left alone and one more is clipped, which a `>` to `>=` flip would break. The 400-character case asserts the length is exactly 300, not just at most.
- **Two replay entries are pinned as having an unserved query, not made to pass.** `You Better Run` and `Heartbreaker` are logged picks, not `missing` entries (the plan anticipated only a `missing` entry), but the same condition applies: the 2026-09-25 logs hold only each song's first query, and `findSong` now also issues the loose query (#61, 2026-09-29). `EXPECTED_UNSERVED` names the one loose query each is expected to leave unserved, and the per-entry assertion is an exact match against it, so those two entries are restricted, not exempt.
- **The tally test replays the corpus itself.** The plan moved the tally into a final test that reads counts the per-song tests leave behind; that works in file order but fails under `bun test --randomize` (the auditor reproduced it). It now runs every entry through `replayEntry` and tallies from the picks, so it neither depends on test order nor on a per-song test having got as far as counting. `afterAll` keeps the unserved-query log lines; the tally line is printed by the tally test.
- **The plan's "the corpus holds no performer names" was imprecise, and the replay's top-of-file comment now says what is true:** each entry keeps its own `searchArtist` (the performer, for an uncredited song), but not the setlist-level performer, lead act or credited artist that `searchArtistsFor` tries first, and the logs hold no fallback-query pages. The decision to decline a fallback-chain replay stands on the missing pages.
- **The description test no longer calls 300 "Spotify's limit".** Spotify's API docs state no description limit (community posts say 300), so the test is named for the client's own 300-character limit and says so.
- **Audit round 1 survivors, each reproduced by mutation and then pinned:** one timeout signal shared across the retry loop (a test that every attempt of a retried request gets its own, `[[10_000], [10_000], [10_000]]`); penalties not adding (`total = penalty`, or the largest wins; a live remix is 55, and 155 with a karaoke credit); `.trimEnd()` dropped from the description clip (a cut that lands on a space); the karaoke-artist rule reading only one position (first, middle and last of three credits); and the `\b` anchors on the live/concert, demo, tribute and remix rows (a title word that merely contains a marker: Alive, Concerto, Democracy, Attribute, Premix).
- **Declined, in writing:** the `\b` anchors on the karaoke, commentary, instrumental and sped-up/slowed/nightcore rows, the leading anchor on the demo row (a word would have to end in "demo" or "rehearsal"), and the trailing anchors on tribute and remix. No ordinary title word contains "karaoke", "commentary", "sped up", "slowed" or "nightcore". For instrumental, tribute and remix the anchors only decide whether a longer form ("Instrumentals", "Instrumentality", "Tributes", "Remixed", "Remixes") is penalised, which nothing says is intended; a test would enshrine an accident. The playlist name clip has no test for its `.trimEnd()` either (its one clip test uses a name with no space at the cut); that predates this change and is not in the issue.
