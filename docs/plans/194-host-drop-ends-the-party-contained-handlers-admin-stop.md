### What is wrong

- (`-5`, channel half) A host whose player fails fatally, or twice running, is removed by `noteOutcome` (`runner.ts`, the `removeMember` commit), and `removeMember` closes the party when the member is the host (`party.ts:82-89`). The channel gets "<@host> has dropped out of the party: ..." and nothing says the party ended; the stale Join button then answers "That party has ended". The boundary timer armed for the closed party is left to fire into nothing.
- (`-9`) No handler has a try/catch after `deferReply`/`update`. `commitParties`, `commit`, `accessTokenFor`, `searchTracks`, `buildPlaylist` and every `runner.*` call can reject (a full disk, an unexpected state). The host answers its own "Something went wrong" only when the interaction is neither replied nor deferred (`rackbops-discord-bot src/plugins/host.ts`, the command wrapper), so a post-defer throw is logged by the host but the user sees "thinking..." until Discord expires it, or the picker's "Building the playlist..." forever with the menu gone. Handlers with a defer or update: `handleSetlist` (`:453`), `handlePick` (`:update`), `handlePartyStart` (`:733`), `handlePartyAdd` (`:770`), `handlePartySkip` (`:865`), `handlePartyJoin` (`:951`).
- (`-11`) Only the host can stop a party (`handlePartyStop`, `:901`); one party per guild persists in `parties.json`, so a host who left the server leaves every `/party start` answering "There's already a party" with nobody able to clear it. And `handlePartyAdd` does not require membership while `handlePartySkip` does: a connected non-member can queue tracks and, on an idle party, start playback on every member's player.

### Decisions

- **A host drop ends the party out loud and cancels its timer.** In `noteOutcome`, when the dropped member is `party.hostId`: the notice becomes "<@host> has dropped out of the party: <reason>. The party has ended -- `/party start` opens a new one." (still mentioning only the host, per #190), and the guild's timer is cancelled (`timers.get(...)?.cancel(); timers.delete(...)`) so nothing fires into the closed party.
- **One containment helper, applied at the three entry points, never inside a handler.** `async function contained(interaction, body: () => Promise<void>): Promise<void>` in `commands.ts`: `try { await body(); } catch (err) { required().log?.error("a music command failed after it was acknowledged", err); if (interaction.deferred || interaction.replied) { try { await interaction.editReply({ content: FAILED_LATE }); } catch (editErr) { required().log?.error("...and the failure reply could not be sent", editErr); } } else { throw err; } }` with `FAILED_LATE = "Something went wrong on the bot's side. Try again in a moment."` It wraps a whole handler from the outside, at the three places a handler is entered: the `/setlist` command's `handle` (where `musicCommands` registers `handleSetlist`), `handleParty`'s body (its subcommand dispatch and the status reply), and `musicInteractions` (the Join button and the picker). A throw before any acknowledgement is re-thrown so the host's own wrapper answers it as today; a throw after it (deferred or replied) is answered with the failure line. Wrapping from the outside leaves every handler body as it is, so this change re-indents nothing another lane is editing. The error object goes to the log, never to the channel. A party opened in memory by a commit that then failed stays open in memory: that memory-versus-disk divergence is the store design question declined in #190 and is not this change.
- **A member who can manage the server can stop the party.** `handlePartyStop` allows the host or `interaction.memberPermissions?.has(PermissionFlagsBits.ManageGuild)`; the refusal reads "Only whoever started the party, or someone who can manage this server, can stop it." The success text is unchanged. **No idle expiry:** the admin stop clears an orphaned party, and an expiry would need a clock field in `parties.json` and a sweep rule; declined, and the plan doc says so.
- **Adding needs membership,** checked synchronously before the defer, like skip: "Only people in the party can add tracks -- press Join on the party message first." This reverses #134's "unchanged; out of scope" by decision: a non-member must not be able to start playback on every member's player.
- **No version bump.** The CHANGELOG bullet travels in the PR body (see the steps).
