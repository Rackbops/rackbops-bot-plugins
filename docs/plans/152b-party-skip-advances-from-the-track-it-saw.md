### What is wrong

`handlePartySkip` (`plugins/music/src/commands.ts:767-798`) reads `party` before the defer, then after `await interaction.deferReply()` computes `next = party.queue[party.index + 1]` from that snapshot and calls `runner.skip(guildId)`, which is `advanceParty` (`runner.ts:113-127`): it always moves on from whatever the party's index is now (`advance`, `party.ts:119-129`). Two members who press skip at about the same time both read index N, both defer, and both advance: N+1 is skipped unheard, and the second is told "Skipped to N+1" while the party is on N+2. The same happens when the track ends naturally during the defer's round trip: the boundary moves the party to N+1 and the skip, meant for N, then skips N+1 too. A track queued during the defer is invisible to the stale `next`, so a skip on what was the last track answers "That was the last track" when there is a next one now.

### Decisions

- **The runner refuses an advance from an index the caller did not see.** `advanceParty(guildId, fromIndex: number)` checks, synchronously and before it touches the timers, that the party exists and `party.index === fromIndex`; otherwise it returns `undefined` and changes nothing (in particular it must not cancel a timer armed since -- that timer belongs to the advance that won). `skip(guildId, fromIndex: number): Promise<MemberOutcome[] | undefined>` passes it through; the timer armed by `arm` passes the index it was armed for (`party.index` at arm time), which documents the invariant and guards any future path that moves the party without the runner. Everything after the check (`advance`, commit, the last-track notice, `playCurrent`, re-arm) is unchanged.
- **The command compares before it acts, and reads `next` fresh.** After the defer: `const current = getParty(partiesState(), guildId)`. If `undefined`: edit "The party ended just now." If `current.index !== party.index` (the snapshot from before the defer): edit "The track changed just now -- the party is on **<current track>** -- Artist. Skip again if you still want to." (or "... the party has nothing playing now." when `currentTrack(current)` or `current.trackStartedAt` is undefined). Otherwise `next = current.queue[current.index + 1]` (fresh: a track queued during the defer counts), the last-track answer as today, then `const outcomes = await runner.skip(guildId, current.index)`; an `undefined` answer gets the same "track changed" edit, re-read (it cannot happen on this path, since nothing awaits between the fresh read and the runner's synchronous check, but the branch keeps the contract honest). The "Skipped to **next**" reply is unchanged: `next` was read from the same state the runner advanced from, so it is the track that is now playing.
- **No version bump.** The CHANGELOG bullet travels in the PR body (see the steps); `plugins.json` is unaffected.

## Corrections found by the review gate (added after the plan above, which is kept as it was posted)

- **"The existing `runner.skip("G1")` calls (around `:216`, `:335`, `:388`, `:402-403`)" -- five calls -- is the count at `b7fd15f`.** At the base of this PR `runner.test.ts` has fifteen `runner.skip(` calls (`git grep -c` of the pre-change file), and the signature change makes each of them a type error without an index; all fifteen now pass the index the party is on at that point.
- **Coverage row 2's symptom ("two plays of track two, or a play of track three") is not what the mutant produces.** On the two-track fixture an unguarded second advance runs the party off the end (`advance` parks `index` at the queue's length), so the "two skips" mutant shows up as no `undefined` result, a party `index` of 2 and the wrong plays, not as a play of track three. The tests go red all the same.
- **The timer's guard is not what fixes skip-versus-boundary.** A winning skip cancels the pending timer before it can fire, and a boundary that fires first has already moved the index before a skip is checked -- both are the `fromIndex` check in `advanceParty`. The `armedFor` guard is reachable only when something moves the party without the runner and without cancelling the timer (a party closed by a host drop and reopened in the same guild; the tests simulate it with `resetPartiesForTest`). The `arm` comment said "a skip got there first"; it no longer does.
- **A refused timer fire left its handle behind, and the plan did not say so.** `advanceParty` returns before it touches the timers, so after a refused boundary the fired handle stayed in the `timers` map; the sweep re-arms a party only when `!timers.has(guildId)`, so it would have taken the dead handle for a live timer and never re-armed that party. Reachable only by a party moved without the runner whose next `start` then fails before its own `arm` (which replaces the handle), but unlike the old behaviour (a stray fire cancelled and deleted its own handle) it did not heal. The timer now drops its own handle when its advance is refused (a refused skip has no timer of its own to drop and touches nothing). The check that it is still the handle in the map is defensive: every other path cancels a handle before replacing or removing it, so a timer that fires is always the map's current handle, and the check is an equivalent mutant no test can separate. Pinned by a test that runs the sweep afterwards.
- **The guard compares `index` only.** A party closed and reopened in the same guild at the same `index` would still be advanced by an old timer that was never cancelled (a host drop closes the party without `runner.stop`). Unchanged by this PR -- the old code advanced any party there was -- and not fixed here; capturing `trackStartedAt` beside `index` would close it. The same blind spot means a skip cannot tell "idle at index k" from "just started at index k": a persisted stuck party (not playing, a track queued behind its index) that a `/party add` starts during a skip's defer would still be advanced by that skip, so the track that had just started goes unheard. Contrived (it needs the stuck shape, which nothing writes any more, or two adds inside one defer on a run-off party) and not fixed here.
- **The command's `outcomes === undefined` branch cannot be reached in production**: nothing awaits between the command's fresh read and the runner's synchronous check. The plan says so; the branch is the contract kept honest, and only the test double (`skipRefuses`) exercises it.
- **"The loser is told the track changed" is not literal for a loser whose party closed during the defer**, who is told it ended ("The party ended just now."). A loser whose party ran off the end is told "The track changed just now -- the party has nothing playing now.", so the bullet is literal for that case. The CHANGELOG bullet in the PR body says "or that the party ended".
- **Tests beyond the plan's list:** the command passes a later track's index (`index: 1`) to the runner (the plan's tests only ever had index 0); a party stopped on another track during the defer; a skip from an index the party has not reached; a skip or boundary for a party that is gone; the sweep re-arming after a refused boundary.
