### What is wrong

- `normalize` (`plugins/music/src/matching.ts:50-66`) deletes five apostrophe characters (`:59`: `'`, U+2018, U+2019, U+02BC, `` ` ``) and its comment says typographic apostrophes are covered. setlist.fm titles also carry the acute accent U+00B4 ("Don´t Stop Believin´"), the prime U+2032 and the fullwidth apostrophe U+FF07; those become a space, so "Don´t" normalises to "don t" against Spotify's "dont", and a short title goes missing. `matching.test.ts` pins only the ASCII apostrophe, so deleting the typographic ones from the class leaves the suite green.
- `CHANGELOG.md:343` says karaoke and "in the style of" uploads are "rejected outright". The penalty is 100 (`:77-78`, and `:102` for a karaoke-label artist), but `pickBestTrack` only skips `score <= 0` (`:334`), so a karaoke upload credited to the original artist (72 for a prefix title + 40 exact artist - 100 = 12) is still eligible and becomes `low` on an otherwise empty page; and a candidate titled exactly like the song with artists `["The Beatles", "Karaoke Kings"]` scores 100 + 40 - 100 = 40 and `exactTitle && exactArtist` makes it `high`. `matching.test.ts`'s karaoke cases use artists with no overlap, so neither shape is pinned.
- `CHANGELOG.md:235-239` (1.3.0, Known limits) gives the match log's size as about 0.4 MiB fully confident and about 10 MiB all-missing; that held for two queries per song. Since 1.6.0 a song is searched under up to four artist names (eight queries), and `queries` is kept for any song that needed more than one query (`build.ts`, `findSong`'s last lines), so the all-missing figure is about four times larger and a confident song reached on a fallback name carries candidate lists too. Hand estimates, as the review's were; there is no byte cap and this child adds none.
- `parseDateOption`'s JSDoc (`setlistfm.ts:252-257`) says two spellings and no others, and that `MM-dd-yyyy` is not accepted at all; the regexes (`:269-270`) accept `-`, `/` and `.` as separators, mixed, and read any leading one-or-two-digit group as the day, so `09/08/2026` is 9 August. `CHANGELOG.md:291-292` (1.1.0) lists only the two spellings. The reply names the parsed date (#92), which is the mitigation.
- Comment drift: `recordRun`'s JSDoc (`matchlog.ts:126-133`) says a throwing logger is not guarded here, but `log?.info(summarize(run))` sits inside the `try` (`:144`), so a throwing logger is caught as "could not write the match log" and the save is skipped: the run stays in memory and is never persisted. `flattenSetlist`'s doc (`setlistfm.ts:171`) says "Three kinds of entry are dropped" and lists two. `replay.test.ts:70` calls the corpus "the 27 non-high songs" though three of its baselines are now `high`. `docs/plans/99-karaoke-originally-performed-by.md` says the karaoke-artist rule checks `artistNames[0]`; the code checks every artist (`matching.ts:102`).

### Decisions

- **The apostrophe class gains U+00B4, U+2032 and U+FF07,** written as escapes (`\u00b4\u2032\uff07`) so the source stays ASCII, with the comment naming all eight. Nothing else in `normalize` changes.
- **A candidate whose penalty reaches 100 is rejected before ranking,** which is what the release note has claimed since 1.0: in `pickBestTrack`, `if (breakdown.score <= 0 || breakdown.penalty >= 100) continue;`. The score itself is unchanged (the match log keeps recording it). `high` needs no extra guard: an exact title cannot carry a title-side marker (`isExactTitle` compares the whole normalised title, `:124-128`), and the karaoke-artist case is now rejected before confidence is computed; reviewer B checks that claim.
- **`recordRun` keeps logging before writing, but a throwing logger no longer costs the save:** the info call gets its own `try { ... } catch { /* a logger that throws is the host's problem; the run is still saved */ }`, and the JSDoc says so (`commands.ts` still contains anything the save path throws past the warn).
- **Release notes are corrected in place.** This child edits the 1.1.0 and 1.3.0 sections of `plugins/music/CHANGELOG.md` (that is the fix the issue asks for; the epic's no-CHANGELOG rule is about the Unreleased bullet, which still travels in the PR body). The 1.0 "rejected outright" sentence stays, now true.
- **No version bump.** The CHANGELOG bullet travels in the PR body (see the steps); `plugins.json` is unaffected.

## Corrections found while executing (added after the plan above, which is kept as it was posted)

- **"`plugins.json` is unaffected" is false once the old release-note sections are edited.** `scripts/generate-index.ts` derives each plugin's `releases[].notes` from `CHANGELOG.md`, so changing the 1.1.0 and 1.3.0 sections changes two `notes` strings in `plugins.json`, and `bun run generate-index -- --check` fails until the index is regenerated. It was regenerated with the generator (`bun run generate-index`), not edited by hand: the diff is `generatedAt` plus those two notes, and the `--check` passes after it.
- **"The reply names the date it read" was loose.** A miss quotes the parsed date as `dd-MM-yyyy` (`resolveByDate`: `setlist.fm has no "<artist>" show on 09-08-2026.`), and a build's first line carries the found show's own date (#92, `formatBuildReply`); no reply echoes what the user typed. The `parseDateOption` doc says exactly that.
- **`penalty >= 100` is a threshold on the TOTAL, not a test for karaoke.** Besides the karaoke and "in the style of" markers (100 each), a stack of lesser ones reaches it too: instrumental (45) + remix (30) + live (25) = 100. Two such markers stay eligible (instrumental + remix is 75). The comment in `pickBestTrack` says so and a test pins both sides; whether three stacked variant markers deserve the same rejection is the orchestrator's call (the alternative is matching on the karaoke patterns alone).
- **The `/party add` effect is narrower than "a karaoke upload credited to the right artist".** The title pass scores with `artist: ""`, so a karaoke credit can never earn artist points there, and its title points (at most 100) are cancelled by the 100 penalty. The only way a karaoke upload still had a positive score was an exact title (100) plus the tie-break fraction (0.01 per same-artist sibling on the page): then it was queued as an unflagged `low` pick. The `pickTrackFromQuery` test builds exactly that page.
- **The corpus replay is unchanged by the rejection**: all 27 baselines hold, and the tally test is untouched. `replay.test.ts`'s renamed test also asserts the 3 `high` baselines, so the name cannot go stale the way the old one did.
- **Cites**: the plan's line numbers are to `0a5cc1c`; at this PR's base (`8132190`) the `recordRun` JSDoc is at `matchlog.ts:136-143`, `flattenSetlist`'s doc at `setlistfm.ts:172-186`, and `parseDateOption`'s at `:253-270`.
- **`1.1.0` really did accept `/` and `.`**: the regex and the 1.1.0 entry landed in the same commit (`61d0062`, #40), so correcting the 1.1.0 entry in place is correct history, not a retcon.
